# FreeTokens 定时核验可靠性修复计划

版本：R4，完成四轮设计自审。日期：2026-09-06。

结论：在本轮范围内，没有剩余的已知阻断性设计缺陷；上线仍受第 9、10、13 节验收条件约束。本文是待实施计划，不是运行可靠性的实测证明。

本文件只提出计划，没有修改应用代码、部署配置、调度或密钥，没有触发收费调用或发送消息。“通过审查”指没有已知的阻断性设计缺陷，不代表实施后无需测试。

## 1. 目标和边界

解决三件事：任务中断后可安全恢复；停止、延期和失败可被发现并通知；页面准确区分检查和人工核验。

本轮不改站群定位，不扩充来源，不自动批准正式资料，不购买服务，不扩大现有审批机器人 GitHub PAT 权限。费用时段沿用已有配置意图；上线前核对配置，不把代码中的折扣注释当作当前价格事实。

最低交付不是“任务变绿”，而是能够解释每个来源处理到哪里、下一步是什么、哪些调用不能自动重试。

## 3. 必须成立的不变量

1. 收费请求发出前，远端必须存在确认成功的调用意图记录。
2. 请求可能已发出但没有可信结果时，不能自动重发，不能用备用供应商再试一次。
3. 已有有效持久结果时，发布重试不得重新调用模型。
4. 检查成功、提取成功、候选发布成功、人工审核通过、通知 API 接受是不同事实。
5. 没有可用供应商是配置阻塞；费用窗口外是延期；二者均不得伪装为成功。
6. 旧运行完成不能覆盖新运行状态；单个来源恢复不能关闭其他来源的问题。
7. 原始提示词、原始模型响应、凭据、私有地址和错误堆栈不进入公开状态。
8. 正式 source hash 和 last_verified 仍只由现有人工审核路径推进。

## 4. 持久状态：复用仓库，但隔离执行和数据

新增 scripts/check_state.py、scripts/check_models.py，使用现有 GitHub App 已具备的仓库写权限，在专用 automation-state 分支保存版本化 JSON。不扩权 daemon/gh_client.py 的 PAT，不把现有 daemon/journal.py 的辅助日志当作可靠状态库。

这是公开仓库：仅保存批准纳入检查的公开来源标识、内容摘要、版本号、固定错误码、运行编号、时间和经白名单验证的结构化提取结果。候选仍按现有公开候选规则校验；不得直接上传抓取原文或整个模型响应。敏感内容检查不通过时停止公开写入并记录不含内容的错误码。日志采用结构化错误分类，不打印第三方原始异常体。

状态分支不合并进 main，不从该分支执行脚本、安装依赖或加载配置。执行代码始终来自可信 main；JSON 设置 schema、大小及条目数量限制，拒绝未知版本和路径穿越。实施时收紧工作流分支/path 触发条件，确保写状态不会触发网站发布或新的检查循环。

记录分四类：

- observation：来源、完整内容 hash、抓取时间、来源配置版本。
- call：call_key、请求配方版本、owner、attempt_id、状态、结果摘要、允许公开的结构化结果。
- publication：候选 manifest hash、分支名、提交 SHA、PR 编号及发布状态。
- run：逐来源结果、覆盖范围、延期时间、固定错误码、收尾状态。

call_key 对实际发送的规范化消息、provider/model、参数、提示词与 schema 版本、来源标识进行摘要。不得只用 run_id 或日期去重；也不得把与提取无关的平台元数据 hash 放进收费键。完整来源 hash 和请求输入 hash 分开保存，便于识别截断后请求相同但页面内容不同的情况。

并发控制采用远端分支提交的比较后写入：读取 head，以它为父提交生成变更，仅允许普通 fast-forward push。遇到竞争重新读取并按状态语义合并，最多 3 次；禁止 force push 和以本地文件覆盖整个远端状态。调用占用以远端成功的状态转换为准，不以 runner 上的锁文件为准。

push 超时不等于失败：查询远端是否包含本次唯一 operation_id。无法确认时停止后续收费动作，交由恢复任务协调。

## 5. 收费调用状态机和恢复

新增 scripts/check_runner.py 编排；scripts/extract.py 保留提取、验证能力，取消隐式跨供应商重试。

| 状态 | 含义 | 自动行为 |
|---|---|---|
| ready | 满足来源、配置和费用条件，尚未占用调用 | 竞争建立 intent |
| intent | 已持久占用本次收费调用 | 仅持有该 attempt 的运行可发出一次请求 |
| result_saved | 结构化结果已验证并在远端确认保存 | 直接继续候选生成/发布 |
| uncertain | 可能已请求但没有可信持久结果 | 禁止自动调用；通知并提供处置入口 |
| rejected_result | 收到响应但解析或校验不通过 | 保留本次调用已发生的事实；不自动换模型重试 |
| deferred | 费用策略暂不允许 | 到 next_eligible_at 后重新做调用前检查 |
| blocked_config | 无符合策略且具备凭据的供应商 | 配置修复后再评估；不循环报成功 |

OpenAI 客户端显式设置 max_retries=0，保持请求超时；其它封装层同样禁止隐式收费重试。只有明确未进入收费调用的抓取、查询、Git 读写可以有限退避重试。

intent 包含 run_id、run_attempt、claim_id 和创建时间。恢复进程即使持有相同运行编号，也不得重放遗留 intent；只有本进程刚完成并确认的占用转换可以进入发送步骤，工作流 rerun 属于新的 run_attempt。租约过期只用于识别失联，不允许另一运行夺取后再次调用。进程可能恰好在响应到达后、结果持久化前崩溃，这种情况无法实现自动恢复且绝对不重复收费；计划选择停止自动重发并标记 uncertain。

人工处置命令只支持：附加经验证的已有结果、放弃该调用、在确认旧运行已停止后批准新 attempt。新 attempt 必须有操作者、原因和明确授权记录；不能删除旧 intent 伪装成首次调用。迟到结果仅允许写回相同且仍有效的 attempt，禁止覆盖已结束或被替代的状态。

增加硬性费用边界：单次请求显式限制输出 token；按运行及来源设置最大新增调用数，并使用持久 intent 计入额度，不能因换 runner 而重置。uncertain 也占用额度。未配置这些上限时 fail closed；具体真实费用预算由受控验证前的明确配置决定，不在本计划擅自填入金额。历史结果复用还必须满足独立的有效期配置；过期后标记 needs_refresh，不自动放弃去重账本再调用。

费用窗口外不自动换到未知成本的服务。配置必须包含时区、允许时段、可用供应商、明确允许的 fallback 和 next_eligible_at 算法。每次请求前重新检查时段；已开始请求跨过边界不强行取消。到期后的下一次现有计划运行负责恢复；超过下一运行窗口仍未恢复则告警，而不是无限 deferred。

## 6. 抓取、候选与发布

scripts/fetch_sources.py 增加显式输出目录参数，工作流传 RUNNER_TEMP 下本次运行专用目录。停止跟踪 .cache/changed.json；保留 .cache/hashes.json 为批准后基线，不在抓取时提前推进。

输入文件丢失是流程错误；存在且为空才是 no_changes。逐来源写抓取结果，部分失败不丢弃成功来源。抓取文本与摘要必须来自同一份内容；不再让两次抓取悄悄混用。提交审核时仍按现有规则重新验证在线来源。

已提取但平台元数据改变时，可以从持久结构化结果重新包装候选；必须重新校验来源授权、内容版本、schema 和平台当前基线。与旧来源内容不再匹配时不得包装为当前有效候选。多来源同平台不绕过现有 platform_hash 冲突校验。

候选标识包含来源版本及候选 schema/配方版本；同 ID 内容不同必须报冲突。拒绝、批准、取代的记录保留墓碑，防止同版本被反复生成和收费。来源再次出现历史相同内容时，必须检查当前批准基线；需要再次提交的真实回退变化可复用合规结果，但不能把历史批准等同于当前已处理。

新增 scripts/publish_candidates.py：

1. 从最新远端 main 建立干净工作树，只复制 manifest 中经过校验的候选。
2. 无有效候选时返回 empty，不执行 git add 不存在目录。
3. 使用 manifest 摘要确定稳定分支和 publication_id。
4. 重试前先核对远端提交、PR 是否存在以及是否已合并；不得仅因本地返回异常就再次创建。
5. PR 被人工关闭则记录停止，不自动重开；合并冲突只重建候选发布基线，不重新调用模型。
6. PR 合并政策沿用现有规则；正式平台资料仍需人工审核。

工作流收尾对成功结果尝试持久化和发布，再单独计算结论：来源失败会保留失败结论；部分成功不能被一个绿色总状态掩盖。runner 被强制取消或杀死时不能依赖 finally/always 完成，恢复必须依赖远端记录。

## 7. 告警、漏跑检测和监控自身故障

新增 daemon/check_monitor.py 与 daemon/alert_store.py，在现有服务器运行，每 5 分钟读取仓库工作流及状态。现有 Watchdog 的审批超时取消职责保持独立；监控线程不能因查询异常退出主循环。

运行告警统一由服务器 monitor 发送，避免 CI 和服务器各自重复发送。复用现有飞书发送能力与已配置管理员，不在文档或公开记录写入接收者标识。现有候选通知属于另一类事件，不能冒充运行健康通知。

使用独立 SQLite 事务保存 incidents 和 outbox；incident 状态变化与发送任务在同一事务提交，采用唯一 event_id 防止重复入队。数据库必须放在容器持久卷，检查可写性、完整性并有备份。数据库不可写时监控健康状态立即降级，不能只在日志中吞掉错误。

发送器区分 pending、api_accepted、retry_wait、delivery_unknown、exhausted。HTTP 200 仍需检查飞书业务码；超时可能已送达，不承诺严格只发一次。有限重试使用同一事件编号，建议 1、5、15 分钟后各一次，仍失败则 exhausted 并保留待处置记录。恢复通知也经过同一 outbox。api_accepted 只代表接口接受，不代表用户已读。

告警内容固定包含：故障阶段、影响范围、最后成功时间、错误码、下一步、Actions/PR 链接。禁止携带原始模型输出和密钥。相同未变化故障不每 5 分钟发送；首次、性质变化、恢复通知，并对持续未处置故障每 24 小时最多提醒一次。

调度按当前北京时间 01:30、04:30、07:30 建立期望窗口，初始启动宽限 180 分钟，并单独限制执行超时。人工 dispatch 不抵消应有的计划运行记录。GitHub 延迟和可能不产生 run 的情况要分别表达为“尚未观察到计划运行”，不能虚构确切排队原因。实施时拆分等价的三条 cron，记录 event.schedule，降低窗口归属歧义。窗口键包含 workflow、计划时刻和日期；同一运行只能归属一个窗口。超长延迟无法确定归属时保留 unknown，不补造成功。独立监控预置期望调度，因此工作流被禁用或根本没创建 run 也能检测。期望配置由受审变更同步更新，监控启动采用明确定义的生效日期，不补发上线前所有历史漏跑。

GitHub API 失败、限流时报告 monitoring_unknown，不能当成“没有失败”。恢复查询后补查游标以来的事件，按来源、阶段和版本核对恢复条件，不能用下一次绿色运行关闭全部 incident。具体规则：抓取故障须由该来源后续成功抓取解除；发布故障须确认对应结果已经入 PR 或被明确处置；uncertain 只能由人工处置解除；通知故障须接口成功接受其重试事件；历史漏跑保留 missed 事实，下一有效计划运行仅结束当前停摆告警。

服务端 heartbeat 保存最后一次成功查询及自身循环时间。飞书断网、服务器宕机、GitHub 不可访问同时发生时无法保证实时通知；不把此情况包装为已解决。上线门槛包括一个独立于该服务器的心跳检查和独立通知通道：先检查是否已有设施可复用；若没有，提交明确配置及接收目标后按授权接入，未完成不得宣称告警闭环已交付。外部检查必须同时看心跳新鲜度和监控降级字段，不能只看 HTTP 200。

## 8. 网站表达

TelemetrySweep.astro 将 last_verified 明确标注为“最近审核核验”；PlatformGrid.astro 删除固定日期回退，无值显示“尚未核验”。不要因一次自动任务跑完更新所有条目的审核日期。

另展示“最近自动检查”：最后完成时间、覆盖来源数、失败/延期数量及数据更新时间。无来源配置的条目不计入已检查。没有状态、状态超过 15 分钟未更新或监控异常时显示“状态暂不可确认”，绝不回退为正常。

公开摘要由 monitor 从经校验状态生成，只含上述聚合字段，不暴露调用账本。实施前确认静态站和机器人实际部署位置；建议在现有主站 Nginx 增加只读 /ops/check-status.json，文件保存在独立持久目录，通过原子替换发布，不写入不可变网站 release 目录。跨域只允许现有站点读取，浏览器不携带凭据，缓存最多 60 秒。后台依据服务器 UTC 计算时间，前端本地时区只负责展示。

如果独立状态路径尚未部署，先上线日期语义修正及 Actions 链接；不得用旧静态摘要冒充实时监控完成。状态展示不应阻塞网站主体加载。

## 9. 实施顺序及每步退出条件

### PR A：阻止丢结果和盲目重复收费

涉及 update.yml、discover.yml、fetch_sources.py、extract.py、新增 check_models/check_state/check_runner/publish_candidates 以及针对性测试。

先短暂停用两项自动调度，保留人工入口但默认 dry-run；盘点已有 candidate/PR，导入可验证的结果与终态。历史上“模型成功、候选未提交”的记录不能默认为未执行：无法从可信日志或保留产物还原的来源版本标记为历史待确认。先消化已有可恢复结果，再决定是否批准新调用。

退出条件：离线故障注入通过，Git 竞争/断连恢复不重复调用，空结果成功、部分成功可保存、费用延期可恢复；保留现有审核回归测试。

### PR B：运行监控和通知闭环

新增 monitor、SQLite outbox、有限重试、调度窗口和独立心跳检查。完善服务持久卷、启动健康检查和运行手册。检查已有 GitHub 凭据权限和飞书配置，不读取或输出密钥值。

退出条件：使用测试事件验证失败、漏跑、延期逾期、部分恢复、发送失败、服务器心跳失联；实际外发按既有授权和确定接收范围执行。只有日志测试通过不算通知链路验证通过。

### PR C：页面时间及小范围恢复调度

上线日期纠正和可判断新鲜度的状态摘要。先 dry-run，随后一个批准来源、一个调用预算内的受控运行，再恢复原有三个时段。至少观察一个完整调度周期及其末次启动宽限，确认不漏报、不误报正常间隔。未完成的外部告警条件必须明确列出，不能以“后续优化”隐藏。

## 10. 必须通过的故障注入验收

测试使用假供应商计数器和本地临时 Git remote，不消耗真实模型额度。通知使用可控制业务码、超时和响应丢失的测试服务。

| 场景 | 必须观察到的结果 |
|---|---|
| 调用前状态写入失败 | 模型调用计数为 0 |
| 两个运行抢同一 call_key | 最多一个自动调用，另一个等待或复用 |
| intent push 成功但返回丢失 | 读取远端确认；不能再次占用并重复调用 |
| intent 保存后、请求前崩溃 | 变为 uncertain；不以租约过期自动重发 |
| 响应返回后、保存前崩溃 | uncertain；通知明确需要处置 |
| 结果保存后、Git 发布失败 | 重试发布；模型计数不增加 |
| PR 创建/合并返回丢失 | 查找既有 PR/提交；不重复发布 |
| 4 个来源中 1 个失败 | 保存其余成功结果；失败不被隐藏 |
| 无变化、无候选目录 | 明确 no_changes/empty，无 pathspec 失败 |
| 输入文件丢失 | 明确流程错误，不能视为无变化 |
| 窗口外、fallback 无凭据 | 不收费；延期或配置阻塞可区分 |
| 下一允许窗口到达及再次错过 | 前者恢复评估；后者产生逾期告警 |
| 人工关闭 PR、拒绝候选 | 不自动重开、不重复收费 |
| 多来源同平台、新旧运行乱序 | 不覆盖新状态，不绕过审核基线 |
| 飞书 HTTP 200 但业务失败 | 不记录 api_accepted |
| 飞书超时但实际接受 | 标记未知；有限重试可识别同一事件 |
| monitor 重启、SQLite 满盘 | 事务状态不丢；故障对外可见 |
| 计划时段间隔、排队延迟、人工运行 | 正常空档不报错；漏跑不能被人工运行掩盖 |
| 服务器停止、GitHub API 失联 | 独立心跳或监控降级告警可验证 |
| 公开状态含未知字段/敏感内容 | 拒绝公开，不输出原始内容 |
| 页面状态过期、缺失 | 显示未知，不显示正常或伪核验日期 |

## 11. 回滚和运维约束

出故障先停新增收费调用，保留只读监控和结果发布恢复。不能简单回滚到没有持久账本的旧提取脚本后重开调度。

状态 schema 必须版本化；新版本发布前测试旧记录读取。回滚版本不能读取时停写、停收费并告警，不清空分支。SQLite 迁移先备份，禁止启动时自动重建来掩盖损坏。

保留去重墓碑，不因常规日志清理删除调用事实。结构化结果是否清理由独立保留策略决定；若结果已经过期或清理，不能将其视为从未调用，重新提取需要明确授权。Git 分支删除文件不会清除历史，因此只能写允许长期公开的数据。

维护手册列出每个固定错误码的处置命令、状态前置条件、负责人角色、下一步时间。uncertain 的处置不要求用户反复发消息试错，而是给出可核对的来源、运行、已知证据和一次明确决策。

## 12. 滚动 review 记录

### R1：恢复边界审查

发现：辅助 journal 不具备事务语义；“模型返回就能保证恢复”不成立；发布重试可能再次收费。

修订：独立可靠状态，收费前 intent，响应丢失进入 uncertain，结果与发布拆分。

### R2：并发、公开数据及告警审查

发现：租约接管会造成重复请求；公开状态可能泄露内容；CI/服务端双发送会重复告警；固定空闲阈值会误判夜间任务；同机监控不能发现自身停机。

修订：过期不自动接管收费调用，公开白名单与可信代码隔离，单一通知拥有者和 outbox，调度窗口判断，独立心跳成为交付门槛。

### R3：迁移、费用与恢复判定审查

发现：历史成功调用可能被迁移遗漏；同 run 的恢复逻辑仍可能误发请求；缺少单次输出和总调用数上限；历史结果可能过期；旧代码回滚会绕过去重；“恢复”缺乏逐阶段判据。

修订：历史不确定记录导入并阻止自动重发；只允许当前进程新建的已确认 intent 进入发送；增加 token/调用数上限及失效结果处置；回滚必须保留账本约束；逐阶段列明恢复判据。

### R4：交付完整性与矛盾复查

对照第 3 节八条不变量检查了正常路径、并发、确认丢失、断电、乱序、凭据缺失、来源变化、通知故障及回滚路径。再检查：公开 Git 历史不可真正删除、同机监控盲区、计划日期归属、发布和人工核验语义、上线暂停是否造成误报。

最终补充：公开数据必须允许长期留存；超长排队归属不明显示 unknown；监控配置显式生效时间；维护暂停必须有到期时间；独立告警和真实预算作为恢复收费调度前的硬门槛。

设计审查结论：上述已发现问题都有明确处理规则或失败时停止的规则，没有以无限重试、吞掉异常或假成功掩盖问题。本次没有执行应用测试，故障注入表是待实现的验收规范。以后若实测出现新反例，重新打开相关审查项，不维持“完美”结论。

## 13. 恢复生产调度前的硬门槛

- **预算配置**：实际 provider/model、允许时段、输出 token 上限、运行/来源调用数上限已校验；不确定调用仍计入额度。
- **持久化**：远端 CAS、状态分支触发隔离、SQLite 持久卷与备份已验证；历史未决调用已导入。
- **通知可达性**：已配置管理员收到一次受控测试；接口接受与人工确认分别记载。外部心跳检查已确认能发现主监控失联，并通过独立通道报告。若现有设施不满足，先完成接入，不以假设代替验收。
- **维护窗口**：暂停调度期间写明开始、到期和原因；监控展示维护状态。到期未恢复必须告警，不能永久静默。
- **质量与回滚**：第 10 节的故障注入通过；既有人工审核测试通过；验证过停止收费但继续监控的回滚操作。
- **生产验证**：干跑后，只进行明确预算内的受控真实调用；观察一个完整调度周期后再签收。任何门槛未通过，保持停止新增收费调用，保留只读诊断和可恢复结果发布。

实施顺序不得倒置：先建立去重与保存能力，再打通告警闭环，最后恢复自动收费任务。
